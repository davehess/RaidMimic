# Decisions inbox: 2026-11-17

### 604. [web] Light mode is parchment, never paper white; looks are tokens only (2026-11-17)

**The call.** The guild lead, on the first light look of the raidmimic.com redesign mocks: *"can we not do bright white
for the light mode? make it parchment - I was damn near blinded looking at that in low light."* And the day before, on
why looks exist at all: *"ideally I could have themes on this site because it might get annoying to look at the
engraved style all the time."*

- **Light mode is parchment on every surface we build** (raidmimic.com, wolfpack.quest, Mimic's local pages if they
  ever get one): no white or near-white page or panel. The mock values: page `#d6c7a6`, panel `#dfd1b2`, row `#cdbd9a`,
  line `#b8a582`, brown ink `#2b2116`. That puts the page at 58% luminance and panels at 65%; the rejected first try was
  88% / 97% (`#f5f1e8` / `#fffcf5`). Every text and status colour stays at or above 4.5:1 on page, panel and row (green
  `#145230`, orange `#723705`, red `#82241e`, blue `#1f4178`, gold text `#5e3e06`; the gold button carries dark ink).
- **Looks change tokens only, never layout:** a visitor picks Titles (Engraved or Plain, which swaps `--display`) and
  Mode (Dark, Light, System). One page works in every look, so a look costs one block of values. Guild themes keep
  their own slot: the guild sets accent and logo, the visitor sets titles and mode.
- **Picked later the same day** (the guild lead: *"default to dark mode, include all four versions so we can toggle
  between them. accents can be per person or per guild."*): **Dark is the default**; all four looks (Engraved or Plain
  titles × Dark or Parchment) are offered as four tiles in the Aa menu, remembered per device and per account. The
  titles default was not stated; Engraved is assumed (the recommendation) until the guild lead says otherwise.
- **Accents, per person or per guild, from a short list** checked in both modes: Gold (Raid Mimic's own), Silver,
  Violet, Teal, Rose. Never red, green or orange (bad, good, warning) and never blue: a Frost accent was rendered and the
  plane marked "now on" (blue) stopped standing out among the cleared ones. On parchment a light accent fill separates
  from the page at only 1.5 to 1.7:1, so bars and the current-tab line use the dark accent there and filled buttons carry
  an ink outline.
- Open on the Desk: which wins when a person and a guild both set an accent (recommended: the person's, then the guild's
  on its own pages, then gold), and narrowing today's guild theme (`web/lib/guildThemeCore.ts` lets a guild set any
  background and text colour, which would paint over parchment; recommended: guilds keep accent, logo and Discord colour
  only), and whether wolfpack.quest gets the same menu.

**Where it landed.** Mocks on branch `draft/rm-redesign-2026-11-16` (`v2.css`, `guild2.html`, the `look-*.png` and
`accent-*.png` pictures; the Aa menu works by clicking there). The Desk card `rm-redesign`: pictures L0 to L4 and A1 to
A3, follow-ups `rm-redesign-looks` (answered), `rm-redesign-accent-order`, `rm-redesign-guild-theme`,
`rm-redesign-looks-wq`. Nothing on beta or main yet.

### 605. [infra-costs] Guild subdomains: Porkbun keeps the DNS; one Vercel domain per guild; no nameserver move (2026-11-17)

**The finding.** With the Porkbun connector attached (the guild lead, 2026-11-17: *"perhaps we do the subdomains there"*), a
read-only look at raidmimic.com showed the wiring is already done at the registrar: Porkbun nameservers, DNSSEC on (one DS
record, algorithm 13), and a wildcard `*.raidmimic.com CNAME cname.vercel-dns.com`, plus the apex A record, `www` and `b`
CNAMEs, Porkbun mail forwarding (MX + SPF) and two leftover `_acme-challenge` TXT records from an earlier wildcard-certificate
attempt. The Vercel project (`quarmparse`) answers only names added to it: `wolfpack.raidmimic.com` and `b.raidmimic.com` are,
and an unlisted name reaches Vercel through the wildcard and is dropped.

**The call (recommended, waiting on the guild lead's go for the automation).** A new guild's address is one Vercel API call,
adding `<slug>.raidmimic.com` to the project; Vercel then issues that name's certificate itself (HTTP challenge, which works
because the wildcard already points at Vercel). No per-guild Porkbun record, no Vercel Pro wildcard, no nameserver move, so
mail forwarding and DNSSEC are untouched. Hobby caps a project at 50 domains (16 used today); past about 30 guilds, revisit
(Pro, or moving DNS to Vercel with DNSSEC switched off first). Supersedes the "Pro plan, nameservers at Vercel" line of §490
and the self-host wizard §3 (both now point here).

**Access.** The Porkbun connector (hosted MCP at `mcp.porkbun.com`, its own "(connected app)" key, scoped by the guild lead to
"Manage, but no purchases"). A first attempt stored the two Porkbun header keys as network secrets, but the secure form keeps
one header per host, so only `X-Secret-API-Key` remained; that half-secret does nothing and can be deleted. Note for anyone
testing from a cloud session: the egress proxy re-signs TLS, so certificates seen from inside the container are not the real
ones; check with the Vercel API or a certificate-transparency log instead.

### 606. [web] Outside design skills: take rules, not skills; our own design skill rewritten to the 2026-11-16 standard (2026-11-17)

**The ask.** The guild lead: *"look at these repos to help with some better design"*: benjitaylor's `stageshow`, Vercel
Labs' web design guidelines, Anthropic's `frontend-design`, and Kubai Icons.

**What was found.**
- **Our own `frontend-design` skill was the bigger problem.** Every design session loads it, and it still said
  "monospace everywhere", listed the August hex values, and named a member: it contradicted the 2026-11-16 standard
  (§603, `docs/DESIGN-theming.md` §8), a likely contributor to the page-to-page drift.
- **Anthropic `frontend-design`** (Apache-2.0, one file, no hooks): ours was adapted from it; upstream has since added
  generic-tell lists, typography don'ts and copy rules worth having.
- **Vercel `web-design-guidelines`** (MIT): the skill fetches its rules live from an unpinned `main` on every run, a
  supply-chain risk in a public repo, and about 70% duplicates impeccable's detectors. A handful of rules are new to us.
  Its sibling `react-best-practices` (MIT, static, about 70 rule files) is the more useful of the two for `web/`.
- **`stageshow`** (MIT): a React toolkit with dependencies and Playwright scripts for faux product UI in marketing
  heroes; only its craft notes for mocks apply to us.
- **Kubai Icons**: the icons are MIT (979 of them), but the skill is source-available and forbids copying, adapting or
  translating its instructions, so its rules cannot be folded into ours. Its style is coloured, layered app icons with
  hover animation, a poor fit for overlays read mid-raid. Our own drawn set (`web/components/PlateIcons.tsx`) is the
  consistent path; about 110 emoji-as-icon lines remain on web pages and every overlay uses glyphs.

**The call (session, routine).** No new skill is vendored. `.claude/skills/frontend-design/SKILL.md` is rewritten: it
points at `tokens.css` and §8 instead of carrying values, states voice B and the AA floor, drops the member's name, and
adds short paraphrased lists (credited) for generic tells, copy, web hygiene, and mocks. Two Vercel quick wins shipped
to beta (29fc1e44): `color-scheme: dark` and a `theme-color`. A grey-contrast fix was not needed: beta's design
standard already raises `--wp-dim` from 3.8:1 to 6.8:1.

**Open (Desk).** Whether to vendor a pinned, trimmed copy of `react-best-practices` (async, server, bundle and
hydration rules) for `web/`; and the icon direction (our drawn set replacing emoji, vs a library).
**Picked the same day:** both A. Icons: our drawn set, website only (overlays keep glyphs until one is tested in a raid).
React rules: a trimmed, pinned copy (`.claude/skills/react-next-rules`, on main). Icons, first batch on beta
(99e036d9, 61d1ea03): 11 new drawn icons in `web/components/PlateIcons.tsx` (17 in all) replace the emoji on /pop, the
PoP guide, the raid review, the parse page and PvP pages; kill blades got crossguards so they do not read as ✕ at text
size. Left on purpose: status marks (✓ ⚠ ✕ ★), emoji inside prose, tooltips, SVG text, mocks, page previews and data.
Still to do (second batch): the remaining ~900 emoji hits on nav, search, inventory, admin and fun pages, and the parse
page's tank and heal headers.

### 609. [bot-discord] Other guilds get a small new Raid Mimic bot, not Wolf Pack's (proposed; picks recorded) (2026-11-17)

**The ask.** The guild lead: *"what do we need to make sure the RaidMimic discord bot works for other guilds"*. Measured
across the bot code, the live database and Discord's docs; the full checklist is `docs/DESIGN-raidmimic-hosted.md` §12, and
§2 carries a re-measure (the guild RLS key is live: `bot_kv.guild_rls_status` key_ok and flag_on, 2026-11-17, so the
open-items step "import the signing key, set flag_guild_rls=1" is done).

**The finding.** Wolf Pack's bot is one server per process (commands registered to one server, one server id and one
guild tag read in dozens of places, no `interaction.guildId` checks), so adding it to another server would write that
server's actions as Wolf Pack's. The database is mostly ready (guild tags, guild-aware read rules, the server-to-guild map)
except four natural keys and the `'wolfpack'` defaults. Discord: no special permission to read events
(permissions 309237730304 cover read + post in one channel), verification required at 100 servers, and privileged
intents need approval past 100, so a shared bot should use none.

**Recommended (Desk card `rm-bot`, when: week):** A, a small new Raid Mimic app beside Wolf Pack's bot, multi-server from
day one (import + raid cards first; global commands; no privileged intent; owned by a Discord Developer Team). B (make
Wolf Pack's bot multi-guild) and C (a copy per guild) are on the card.

**Picks recorded the same day (Desk):** `rm-redesign` menu **B** (one site, roles add a tab); `discord-import` **A** with
every follow-up as recommended (members-only by default, the shared bot reads read-only, seeded aliases from the bosses
list's short names plus officers' own, sign-up bots later); `kill-icon` **N7** (solid shield, blades cut in, also for raid),
on beta (5b196277).

### 608. [web] Hosted-guild setup imports raids from the server's Discord events (2026-11-17)

**The call.** The guild lead: *"Part of the setup for guild leaders and officers doing events should be importing from
their discord events. Everyone does these differently, but we can at least grab the schedule and keywords from these
posts if they bring raidmimic into their server."* Four guilds' event lists were shown (titles like "Tactics (RZ) / Water
Minis", "PoV Aerin'Dar … Loot: mains>alts", "Loot remains P > S > A", weekly repeats).

**What it can rely on.** Discord's scheduled events give exact UTC times, the repeat rule, the channel or location, the
cover image and the interested count, read over REST with the bot in the server (no admin permission; Wolf Pack's bot
already does it in `utils/raidEvents.js`). Titles and descriptions are free text: full boss and zone names match the
catalog, slang needs an alias list (RZ, VZ, AD, PoV, "minis"), and unmatched words stay plain text.

**Rules that hold whichever option is picked.** Member @mentions in descriptions are stripped before anything is shown or
stored. "Interested" on Discord is never counted as a sign-up or a filled seat. An event keeps its Discord id so an edit
or cancellation follows it. Many guilds keep the real roster in a sign-up bot's post (Raid-Helper and the like), which
Discord's event list does not contain.

**Open (Desk card `discord-import`, when: week).** A review then add (recommended), B mirror automatically, C times only;
follow-ups on default visibility (members only, recommended), which bot reads (the shared bot, read-only, recommended),
aliases (seeded, officers add, recommended) and sign-up bots (later, recommended). It feeds the listing table the
`rm-redesign` build needs. Setup checklist row 4a in `docs/DESIGN-raidmimic-hosted.md`.

### 607. [mimic-app] What a Mimic release says: notes or one title, then FB numbers and how to get it; no signing line (2026-11-17)

**The ask.** The guild lead, on the first signed alpha's release page: *"do we need this whole long blurb - is there
something more valuable than that"*. Every release ended with the same line (signed or not, bundles Node, updates
itself); beta releases posted the whole technical commit message to #mimic-releases (v3.1.0-beta.15 listed a test file);
the alpha showed a merge commit's title; and the signing line printed the signer's legal name.

**The call (the guild lead, Desk card `release-notes`: B, plus FB numbers, alpha treated like beta).** Above the `---`
(what #mimic-releases reposts): the newest player-notes block in the push, else one line, the newest non-`sync:`
title; never a commit body. Below it (GitHub only): "Fixes FB-n, …" (numbers from the push's close lines, never a
report's text) and "New to Mimic? Download Raid-Mimic-Setup below. Already have it? It updates itself." No signing line
(the earlier `signing-publisher` pick, A, folded in). Rule for sessions: every Mimic commit that ships carries a
player-notes block.

**Where it landed.** `release-mimic.yml` "Build release notes" reads `github.event.before..HEAD`;
`test/release-notes-step.test.js` runs that script against a throwaway repo; CLAUDE.md's release section. The Windows 7
build (`build-mimic-win7.yml`) keeps its own short text and is not signed; unchanged.
